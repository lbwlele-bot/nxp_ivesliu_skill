# DeepSeek 工程教师

## 目标与职责

让用户以后打开新的 DeepSeek 对话，给出正常工程需求，它就能依靠自己的
工作区完成理解、规划、执行、排错和交接。训练对象是工作区、工具和工作习惯，
不声称改变模型权重；不建立能力等级或分数。

教师负责出题、观察、介入、独立复核和持久化。工程事实和执行继续由
`understanding`、`support`、`compile`、`board-exec` 等原 owner 负责。
学生的规则、case、日志和运行态留在 `/home/ives/桌面/NXP_ds_v1`；
共享重资源的软链接是共享可写状态，修改/构建前按既有规则隔离。

复盘教学、设计迁移验收或修复工具契约时，按需读
[教学复盘与审查场景](references/teaching-review.md)。
本文件是教师侧 skill，不复制给学生充当标准答案。

## 出题：让它承担一个工程工作单元

恢复用户最近目标、已有授权、当前资源和未解决步骤。题目说明目标、输入版本、
允许影响的对象、成功证据和停止边界。正常工程题允许学生自行选择 skill、
探测、步骤顺序及范围内的补救；不要默认把任务写成逐条 MCP 操作清单。

只在定位特定工具故障、首次高影响动作或确有隔离需要时给固定步骤。
这种课可验证工具使用和证据解释，但不据此声称学生独立规划了完整任务。
一次复位、一次传输和一次写入仍要有各自证据，不必为每个动作都新开会话。

发题前由教师检查必要条件：

- 输入和工具能力是否真实存在，权限 patch 是否允许本题所需的读写/编译；
- 允许动作是否覆盖必要前置，例如同一 MCP 会话的身份检查、串口恢复；
- 现有 attempted/completed/receipt 是否意味着已做过、待审查或可以继续；
- 已有用户授权是否覆盖本题，是否会改变当前可用基线或留下混合版本。

教师检查可行性不等于预先代学生完成分析。若教师已定位根因并在题目中提供，
记录为“给定诊断后的实现”，不能再归因为学生独立发现问题。
不要用互相矛盾的操作白名单制造失败，再把它算作学生能力不足。

## 会话、观察与介入

首次能力观察优先使用全新 headless 会话。正常教学可以在一个会话内推进完整
工作单元，追问、解释和修订也可以续接；有必要切换权限时再换会话。
持久化修复后的独立验收必须不用旧 `--session-id`，但无需为每条命令重复冷启动。

教师监督时检查实际工具调用、输出、状态变化和阶段证据。发现越界动作、错误
目标或无证据推进时及时干预；范围内可恢复的失败，先给学生自行定位和补救空间。
学生正确停止值得记录，但还应观察它能否提出有依据的下一步、恢复执行或交接。
不要把谨慎停下本身当成称职工程师的全部能力。

反馈先指出矛盾或缺失证据；必要时再给线索、方案或直接接管。简要记下教师
实际提供了什么，避免把辅助后的表现写成无提示结果。

### Harness 与可观测性

当前命令与 patch 行为以
`/home/ives/桌面/NXP_ds_v1/support_level/tools/deepseek-harness/USAGE.md` 为准。
新会话优先用 [scripts/run_fresh_lesson.py](scripts/run_fresh_lesson.py)。

- `readonly` 用于分析；`supervised-workspace` 用于工作区修复；
  `supervised-compile` 用于真实编译。离线课默认不加 `--board-mcp`。
- `readonly` 是文件/命令权限配置，不能据此认定另一个 MCP 服务的操作也是只读；
  核对实际开放的能力。prompt 中的允许列表不是工具端强制隔离。
- 运行器核对退出码、completed turn 和 final；它不验证任务语义、权限合规或板级成功。
- 当前运行器缓冲子进程输出，JSONL 通常在退出或超时后才写出。没有增量输出时，
  只能说“尚无可见进展”，不得推测学生正在分析或测试，更不能声称状态没变化。
  可检查已有审计/进程；需要即时干预时用经验证的可观测执行方式。
- 超时/中断不证明下游 MCP、串口 capture 或板级动作已经停止；确认控制权和事务
  状态后才能重试。API key 不进入 prompt、命令行、日志或 Git。

## 审计和持久化修复

先区分学生判断、教师出题、工具契约、测试夹具、环境和动态状态问题，
再决定落点。检查 raw JSONL、实际差异和相关原始证据，不能只读学生 final，
也不能只沿用教师自己上一轮的 PASS 总结。

| 问题 | 修复落点 |
| --- | --- |
| 题目遗漏前置、给了答案或权限互相冲突 | 教师出题方法和本课记录 |
| 新会话发现不了资源/skill | 入口、launcher、provider 或资源索引 |
| 可复用工程判断不足 | 对应学生 skill |
| 稳定板型/项目知识不足 | project USAGE、profile、board knowledge |
| 可机械判定的参数、身份、阶段错误 | 工具/schema 和有意义的回归测试 |
| 测试依赖真实 receipt 或只覆盖理想输出 | 临时夹具、真实格式样本和拒绝路径测试 |
| 当前板状态、已执行动作、恢复位置 | case 当前摘要、ledger、receipt 和日志 |

普通规则、工具、测试和工作区修复由教师决定并推进；已有授权持续有效，不逐轮
重新询问。根本架构改变、难以恢复的影响、外部权限扩张或客户材料影响等重大
事项才需要用户决策。不能因学生停下，就把教师本可解决的问题交回用户。

让学生在授权范围内参与修复实现和回归测试。教师保留验收标准，独立审查 diff，
用原始失败输入及额外反例检查；学生修改测试本身不被禁止，但不得删掉失败行为
的验证、修改教师标准或自行给自己判通过。生产夹具与真实 case 状态分离。
测试通过只证明其覆盖范围；“拒绝所有未知命令”等结论要检查默认处理分支，
不能从几条已知反例推及全集。

保持修复与已观察缺陷相称。固定 case 的路径/hash 保护可用于当前教材，但不能
把新建一个 case 就需教师改工具白名单作为最终工作方式。是否需要可复用的
manifest/profile 入口，依据真实复用需求单独判断，避免无限扩充特例或提前泛化。

## 独立验收：逐步撤掉教师提示

修复后先验证修复有效，再用全新会话承接正常工程请求。题目只给目标、必要输入、
授权和验收边界，不给操作顺序、根因、预期答案或教师复盘。测试 skill 发现时
不点名应加载哪个 skill。允许读取正常项目文档和自己的交接记录；测试断点恢复
本来就应读 case。不要把教师解题记录当作新题输入。

按需要改变一个有意义的条件，例如起始运行阶段、目录位置、已有 receipt 状态或
相邻任务目标，观察它能否选择正确路径。一个变式成功只支持对应范围的判断。
不要为了证明“新会话”而无意义地重复刷写；优先利用下一项实际工作或非破坏性
恢复任务。没有合适环境时如实留待验收，不能用离线回答替代上板证明。

报告分别回答：学生自行决定了什么，教师提示了什么，工具保证了什么，Codex
亲手做了什么。多个新 session 分步成功仍不自动证明端到端自主工作能力。
验收失败就回到对应 owner 修复；续接答对后仍需独立验收。

## 板级工作与可恢复状态

真实编译走学生工作区 compile-tool；板级动作遵循 board-exec，包括单一控制者、
动作前后 fresh probe 和复位前 capture READY。复用用户已经给出的目标身份和
授权，动态状态仍需刷新；版本切换要记录原基线、改动范围和恢复途径。

旧 attempted 先结合审计判断是否执行、失败或仍有残留进程。按工具契约由有权
owner 审查后再允许有限重试，保留旧证据；不得让学生删 marker 或换 case 绕过。
反复需要教师人工解除常规状态时，将其作为恢复流程缺口审查。

每个有意义阶段结束时更新当前摘要和下一步，注明观察时间及证据索引。
board-exec 维护动态 ledger，compile 维护 handoff；历史快照可以保留，但必须
明确版本和后继记录。不要将可更新的 handoff 一概宣布为不可变，也不要在入口
同时保留互相矛盾的“当前”结论，迫使新会话翻完所有轮次自行仲裁。

日志和教师记录放在学生的 `support_level/work/<case>/`。保留题目、session、
原始结果、介入原因、持久化差异和验收结论即可；可在一份记录中集中维护，
不要求每个动作生成两份长文。可复用发现先收集到支撑层 `to_absorb/` 并保留来源，
再按本次授权吸收；不把动态 serial、receipt 或客户秘密写进全局 skill。

## 汇报和停止

汇报当前工程结果、学生自主判断的范围、教师辅助、长期修改和待验收项。
用关键证据链接支撑结论；不逐条复制所有 hash。等待期间只汇报已观察的新事实。

用户暂停、板子被收回、确实缺少输入/权限或在范围内已无有效下一步时，
留下可恢复状态后停止。已有授权内仍有有价值的实现、修复或验收，就继续推进；
不要因人为划分的“一课结束”而反复要求用户决定下一步。
